# Performance work

- **Performance (2026-09-29)**: measured with headless Chromium on the GTX 1660 Ti at 1600×900 (`--use-angle=vulkan --enable-gpu --ignore-gpu-blocklist --disable-gpu-vsync --disable-frame-rate-limit`). Findings and fixes:
  - GTAO re-renders the whole scene and cost ~24 ms, so it is Ultra-only now.
  - POOL 10; shadow spots High 1 (refreshed every 3 frames), Ultra 3 (every 2).
  - Sun shadow 2048 on High, 4096 on Ultra, redrawn only when doors or power change (it had been every 2 s).
  - Runtime sun-shaft tracing built a BVH per map mesh, about 0.75 s freezes for a minute after joining. The shafts are now baked into `mods/lighting/sunshafts.json` by `.tools/bake-sunshafts.mjs` (it loads the page with `?bakeShafts`).
  - Normal maps load during loading (ImageBitmapLoader, in parallel). map-materials then runs `renderer.compileAsync` on the scene and viewScene and draws one full frame, so the compiles and uploads happen behind the loading screen.
  - The lighting mod runs `tick(1/60)` at setup so the shadow-caster and sun setup are final before that compile (otherwise every shader recompiled on the first played frame).
  - HD map texture swaps no longer set `needsUpdate` (it forced a program rebuild per swap).
  Result: median 47 → 24 ms, p99 175 → 42 ms, max 930 → 116 ms; ready in about 12 s.
- **Mystery box**: `warm()` also runs `kino.lighting.tag` (LIGHT_CLAMP define, shadow flags), turns off castShadow and frustum culling on the display copies (the first cull of a rigged model computes bounds through its bones), and renders one frame. Spin worst frame 470–580 → about 60 ms.
- **Weapon preloading** (`mods/hd-weapons` setup, last in mods.json so it compiles against the final lights): during loading it fetches every obtainable weapon's viewmodel and animations (loadout, wall guns, boxPool) and runs one `compileAsync` over viewScene (36 weapons in about 3.3 s). It deliberately skips texture uploads, because uploading every gun's HD textures filled VRAM and slowed everything. Targeted preloads do upload: the box's `roll.weapon` as soon as the spin starts (the weapon is chosen then), and wall guns within 260. Taking a box weapon had been a ~370 ms freeze.
- **Mystery box performance** (upstream `mystery-box.js` edit): each weapon's centred display copy is cloned once (`display(id)`, cached in `this.displays`) and reused, instead of a SkeletonUtils clone and dispose on every spin swap (about 30 ms each, up to 20 per second). `warm(renderer,camera)` compiles shaders and uploads every box weapon's textures during loading; game.js and zombies.js call it after `mods.start`, desktop only (skipped on mobile for memory).
- **Frame rate investigation (2026-10-04)**: about 21 FPS at 1280x720 on the GTX 1660 Ti, the same at 320x180, so it is CPU-bound (about 1,800 draws, 500 program switches and 1,570 VAO binds a frame), not fill-bound. The BO3 mod guns cost nothing (same FPS with `bo3-weapons` dropped). Dropping the lighting mod gives about 34 FPS: its extras are sprites, dust, beams (no measurable cost each) and about 150 transparent meshes (about 5 FPS), mostly 103 bulb-glass meshes with 85 distinct materials (one per lamp so each can switch on and off, so they cannot be instanced). Tried and no gain: skipping unchanged bone-texture uploads of the static map props (kept, `world.js stillSkeletons`), batching the bulb glass. Next options: a lighting quality mode or merging the map's static meshes.

## Main menu load (2026-10-05)
Through the public tunnel each request costs about 0.17 s and home.js imported ~35 mod scripts one after another (to run their `prepare` for weapon data) before drawing anything: the map list appeared after 6-10 s (0.6 s locally). Now: mod data patches and scripts are fetched in parallel, then applied in mods.json order; the map grid and hero are painted as soon as `maps.json` arrives (a first paint the full render replaces); the Kino hero image is a 140 KB WebP (`mods/maps/thumbs/kino.webp`; the 2.4 MB PNG stays the social-share image) preloaded in home.html with three.js modulepreloaded. Measured through zombies.terminallysleepy.com: map list 0.7 s, full menu 1.9 s.

- **Transparent double-sided materials (2026-10-05):** three draws a transparent DoubleSide material in two passes (back, then front) and sets `needsUpdate` before each. Kino's 55 lamp-glass materials and ~100 map decals (made transparent by map-materials) re-checked their shader programs twice a frame: `getProgram`/`getParameters` were ~16% of the frame's CPU (CDP profile). The lighting mod now sets `forceSinglePass` on every such material, sweeping each second for late ones. Kino on the 1660 Ti: 35 → 42 FPS empty, 30 → 37 FPS with 24 zombies, worst frames 50–78 → 33–43 ms. How to find it: watch `material.version` change between frames.

Saved = recomputed, verified.
  - map-materials smoothing runs in a worker (`smoothNormals`, self-contained, its source is posted as a Blob worker); normals are swapped in when it answers. Output identical to the old main-thread code (all 1,002 geometries).
  - Result: local browser 24.4/22.0 s → 18.1/16.8 s (cold/warm); Rind through the public site 49/27 s → 36/21 s.

## Frame rate pass (2026-10-07)
Benchmark: Kino, uncapped (`--disable-frame-rate-limit --disable-gpu-vsync`), no zombies, 13 views (spawn x4 yaws + every box location), 2.5 s each, 1600x900, GTX 1660 Ti, headless Chromium. Average FPS (worst view):

| quality | before | after |
|---|---|---|
| Low | 85.9 (51.9) | 83.8 (50.3) |
| Medium | 76.1 (44.5) | 79.5 (48.6) |
| High (default) | 62.2 (38.6) | 73.1 (43.9) |
| Ultra | 41.0 (26.1) | 42.4 (27.6) |

- Still CPU-bound (High at 50% render scale: 65.5). Profile at High: the lighting mod's `renderWorld` ~62% inclusive; three's `updateMatrixWorld` 11%, `projectObject` + `intersectsObject` (culling) 14%, beam-dust updates 5%.
- `world.js`: after `optimizeStaticScene`, the map root computes its world matrices once and its `updateMatrixWorld` only runs when forced (three r185 walks every child even with `matrixWorldAutoUpdate=false`). Kino only (the only `World` user); moving brushes are already outside that root. High 62 → 68.5.
- Lighting: beam dust moves in its vertex shader (`seedA`/`seedB` attributes, shared `dustTime` uniform; same closed-form motion as the old per-frame CPU loop; bounding sphere set from the beam since positions are zero). High → 73.
- Tried, not kept: merging static map meshes (`mergeGeometries` per material within 768/1536 cells). The 1,152 opaque static meshes use 612 materials (384 distinct by properties, 349 colour textures), so only 84–170 meshes merged and draws barely moved (953 → 927–942); over 600 draws are already `optimizeStaticScene` instance batches. Real gains there need texture atlases/arrays.
- Ultra's GTAO pass redraws the scene (1,871 draws vs 955).
- **Ultra AO (2026-10-07, same day):** GTAO no longer redraws the scene for its own depth/normals: `gtao.setGBuffer(depth)` with the main render's depth texture (normals rebuilt from depth), at half resolution (`setSize` halved). The composer swaps buffers an odd number of times a frame, so the scene's depth alternates between its two targets: `renderPass.render` is wrapped to note its target and the GTAO wrapper points `tDepth` of the GTAO and denoise materials at it each frame (setGBuffer again would recompile). The old wrapper that hid transparent objects during GTAO's own scene pass is gone with that pass. Back-to-back A/B: Ultra 40 → 54 FPS (worst view 26 → 38), draws 1,875 → 1,135. Looks the same (screenshot MAE 0.3–0.5% at two views; a third differed by light fade timing); slightly softer: −2.5% mean brightness against High vs −3.5% before.
- **Chunk culling: tried, no gain, removed.** Grouping the 1,272 static map objects into 44 (1,024-unit) or 107 (512) chunks, hiding chunks outside each render's camera (`scene.onBeforeRender`, shadow maps unhiding all): 23/44 or 45/107 chunks culled per view, FPS unchanged in back-to-back A/B (~70.5 vs ~70 at High). The profiler's 14% for projectObject/intersectsObject overstated what culling saves. Note: run-to-run drift is ±3 FPS, so compare back to back.
## The Giant frame rate pass (2026-10-15, user: "fix and optimize the whole game… noticing a lot of bad issues with the Giant… target 120 fps")
Benchmark: `.tools/bench-fps.mjs [map] [quality] [query]` (new, kept): uncapped headless Chromium on the GTX 1660 Ti, 1600x900, no zombies, spawn x4 yaws + every exfil zone x2 yaws, 2.5 s each; prints FPS, p95/max frame time, draw calls and triangles per view. The engine takes `?noMerge`, `?noBatch`, `?noFreeze` to switch each change off for A/B runs.

| The Giant, High | average | worst view | calls (worst) | triangles (worst) |
|---|---|---|---|---|
| before | 40.8 | 24.6 | 5,684 | 17.9M |
| after | 70.9 | 55.4 | ~1,000 | ~4M |

Kino High with the prop batching: 63.2 → 69.6 (worst 41.4 → 49.2), back to back.

What it was, in order of discovery:
- **Props** (`instance-cull.js`, engine, all maps): the BO3 port places 39,929 props as 3,737 InstancedMeshes (per model per 2,048-unit cell). Cell bounding spheres are huge, so three culled almost nothing: 3,450 draws and 16.5M of 17.9M triangles. Now every map-root InstancedMesh goes into a `THREE.BatchedMesh` per material and vertex layout (512 batches; one multi-draw each), originals and their empty cell groups detached from the scene (`detached`). Culling is done by the culler, not three: only when the camera moved 12 units, turned 4° or zoomed, instances outside the view frustum widened by ~10° or smaller than `CULL_PIXELS` (Low..Ultra 6/4/3/2 px; map entry `instanceCullPixels`) are switched off with `setVisibleAt`. Shadow-casting batches (Kino's sun-lit static batches) are culled by size only. Three's own `perObjectFrustumCulled`/`sortObjects` ran over all 40,000 instances on every render and cost more than the draws they saved.
- **Distance LODs**: each prop model over 200 triangles gets two simplified copies (meshoptimizer's simplifier, vendored as `vendor/meshopt_simplifier.js`, MIT, licence beside it) at 25% / 8% of its indices (relative errors .02 / .06), compacted to the vertices they use; an instance switches with `setGeometryIdAt` by on-screen size (LOD0 ≥ 110 px, LOD1 ≥ 40 px, else LOD2). Built at load, ~0.9 s on The Giant. Worst-view triangles 11.8M → 4.5M.
- **three r185 bug**: `setProgram` reads `object.colorTexture` on a BatchedMesh, the class keeps `_colorsTexture`; `undefined !== null` made every batched draw look its program up again (getProgram/getParameters ~15%). `instance-cull.js` defines the `colorTexture` getter on the prototype.
- A material drawn by both a batch and a plain mesh also flips programs every draw: such batches get a material clone (`userData.batchCopyOf`).
- **Level meshes** (`scene-merge.js`, opt-in: maps.json `mergeStatic: true`, `mergeExclude` regex for names mods find or toggle; The Giant `^GIANT_`): 1,657 of 2,099 meshes merged per material and vertex layout into 192 (world space, originals detached, unused geometry disposed). Skipped: skinned/instanced/multi-material/morph meshes, hidden ones, custom-world markers (doors, movers, traps, risers: `userData.marker`). Not on Cheese Cube (its mod toggles named meshes).
- **Static freeze** (`static-freeze.js`, custom maps; Kino's world.js already freezes its root): every non-bone object under `world.root` stops composing its matrix each frame; every 15 frames position/rotation/scale are compared with a snapshot and anything that moved goes back to normal updates for good. Doors slide fine (checked: 108 units open).
- **Idle trap lights**: custom-world gave every trap zone its own PointLight at intensity 0 (14 of The Giant's 23), and three evaluates every point light for every pixel regardless. Zones now carry a plain `{intensity, color, position}` and two real lights (`TRAP_LIGHTS`) follow the lit zones nearest the player (maps/custom.js). That view: 49.5 → 71.7 FPS and the periodic 60-110 ms stalls (GPU backpressure: our render took 12 ms in those frames, the browser held the next frame) stopped. Lights 27 → 16.
- **Two-pass transparent materials** (moved into the engine from the lighting mod, now over the view scene too): a glass material and the viewmodel's decals were flagged needsUpdate twice per draw; `forceSinglePass` sweep once a second on scene and viewScene.
- Visual check: four Giant views screenshot with everything off vs on: identical apart from the moving searchlight beam.
- Not done yet / next: what's left is CPU in three's render loop (~12 ms at the cheapest view: uniform uploads per draw, culling walk, player collision) and the bloom composer; 120 FPS needs more there (and Medium/Low quality get the same props/LOD gains).
- **Loading went black (2026-10-15, user: "before it finishes loading the screen goes black")**: the merge, prop batching (with LOD simplification) and the batch shader compile ran back to back at the end of loading: 2-3 s with no paint, which a real browser can show as a black canvas. The engine now shows 'Optimizing the map' and paints between the steps (rAF + setTimeout), the culler yields every 40 ms while building batches, and the batched originals' geometry is disposed (the batches hold copies, so loading no longer keeps both on the GPU). Headless capture every 250 ms: frames keep coming through the step (it froze ~3 s before); doors, traps and lights still check out.
- **Black window in Rind, round 2 (2026-10-15, user video on Windows)**: the whole Rind window (HTML included, not just the canvas) goes black ~5 s into a Kino load on one try, and 1 s after the map backdrop appears on another; that looks like Chromium's GPU or renderer process dying, which the paint fix couldn't help. Rind hasn't changed since 0.3.2 (its uncapped flags `disable-gpu-vsync`/`disable-frame-rate-limit` date from 0.1). Not reproducible here (Linux, Vulkan ANGLE; the user's Windows uses D3D11 ANGLE). **Diagnostics** added: engine `diag()` sends stages, a 2 s heartbeat (until 20 s after ready), `webglcontextlost`/`restored`, errors and unhandled rejections with the GPU string, JS heap and frame count to `POST /api/client-log` (kino-server; `KINO_DATA/client-log.jsonl`, rotated at 5 MB, signed-in name if any). Read it after the user reproduces. Kino here: heap ~560 MB by ready.

## RAM: decoded textures freed after upload (2026-10-16, user: crash "Not enough memory to open this page")
With the user's profile a loaded map's page used 5.5-6.2 GB (Kino) / 5.7 GB (The Giant), the same with this week's performance changes off; JS heap only ~600 MB. three keeps every texture's decoded ImageBitmap after uploading it: 1.35 GB (Kino) / 1.65 GB (The Giant) of them, every texture held in RAM and VRAM.
- `texture-memory.js` (imported first by engine.js and home.js; `?keepTextures` turns it off): wraps `createImageBitmap` so a bitmap decoded from a Blob remembers it (the compressed file); a prototype accessor on `Texture.onUpdate` (three calls it right after each upload; its constructor's `onUpdate = null` lands in the setter) closes the bitmap. Clone or `needsUpdate = true` on a texture whose image is out re-decodes from the Blob.
- Gotcha 1: an upload needed while the image is out (a clone with other settings, a changed setting like the anisotropy map-materials raises on Kino's textures) makes three size a new GPU copy from the closed 0x0 bitmap and never resize it: black for good (Kino's chalkboard, stage machine, debris). Every texture that touched a released source is recorded and `dispose()`d when the pixels return, so it rebuilds at the right size.
- Gotcha 2: something that re-flags a texture repeatedly turned that into a free/decode/rebuild loop (a Kino load hung > 5 min, and it was live). A source that had to come back once is never freed again (`kept`).
- Context loss: freed images can't be re-uploaded, so the engine reloads the page on `webglcontextrestored` when anything was freed.
- Result (user profile, back to back): Kino ~6.2 → ~4.1 GB, The Giant ~5.7 → ~3.6 GB; ~2.0-2.4 GB of images freed per map. Screens identical (The Giant pixel-exact; Kino differs only by gun sway). Still held: images of things not drawn yet (freed on first draw) and those that had to come back.

## Texture arrays for prop batches (2026-10-16, Der Eisendrache)

Opt-in per map: `textureArrays: <layer px>` in the map entry (`?noArrays` turns it off for an A/B). instance-cull.js batches opaque and cut-out MeshStandardMaterials that differ only by colour/normal map and colour into one BatchedMesh per shader setup (side, alphaTest, roughness, metalness, emissive, normal map or not, program key, vertex layout). Their maps become layers of two DataArrayTextures: allocated by three with `source.dataReady = false` (texStorage3D, no data), then filled with `gl.texSubImage3D` from the decoded ImageBitmaps (32 decodes in flight; released images come back from their files via texture-memory.js `imageOf`; anything not layer-sized is resized with createImageBitmap), mipmaps by `gl.generateMipmap`, then `renderer.resetState()`. Each instance's layer pair is in a float RG DataTexture read in the vertex shader through `getIndirectIndex( gl_DrawID )` (as three reads matrices) and passed `flat`; its colour is the material colour x instance colour (BatchedMesh colours). The shader patch expands `map_fragment` / `normal_fragment_maps` before replacing their texture2D calls (at onBeforeCompile time the shader still has `#include`s: a plain replace silently did nothing and every prop sampled the white placeholder map). Groups split at MAX_ARRAY_TEXTURE_LAYERS. The originals' images are dropped afterwards (`dropImage`) unless something else still draws them. Arrays can't be rebuilt after a context loss: the engine already reloads the page then. Der Eisendrache: 2,179 materials -> 619 batches, worst view 28 -> 42 FPS.
Also: a batch whose instances are all culled is hidden (an empty batch still cost ~10 µs of renderer work).

## texture-memory.js fixes (2026-10-16)
- Several Texture objects can share one image with different settings (colour space, anisotropy, wrapping): three gives each its own GPU copy. The first upload freed the shared image, so the others uploaded a closed 0x0 bitmap and drew black (Bondrewd Premium's first-person arm; 392 such textures in one Kino load). `onUpdate` now checks: an upload that found its image already freed decodes it again and re-uploads (`touch`). Verified against `?keepTextures`.
- Only the main renderer's uploads free images (`setPrimaryRenderer`, engine.js and the menu's stage; `WebGLRenderer.prototype.render/compile/initTexture/copyTextureToTexture` are wrapped to know which renderer is uploading): the HUD portrait, gun icons, Gunsmith preview and menu thumbnails have their own contexts.

## Spawn and first-appearance stalls (2026-10-17, after the user's frame-loss report)
Measured with a scripted 45 s play (kills, rounds advancing, camera turning) on the GTX 1660 Ti host, plus the play-time diagnostics on a scratch server.
- **Skinned bounds** (`skinned-bounds.js`, imported by engine.js and home.js): `SkinnedMesh.computeBoundingBox/Sphere` are replaced by the one-loop `skinnedBox` for every rigged model. Each new zombie measured its body/head meshes on its first drawn frame, ~4 ms each (~16 ms a zombie); now ~0.3 ms each. The sphere is the box's bounding sphere (a little larger than three's, so culling stays conservative). The morph-target fallback calls three's original (`SLOW_BOX`).
- **Shader warm-up** (`warmShaders()` in engine.js, after the instance batches; `?noWarm` skips it): the old load-time compiles (map-materials, the batches) compiled for the screen, but the lighting mod draws the scene into its post-processing target, which needs other program variants, so only what the one warm-up frame showed was really ready. Out-of-view or hidden objects compiled when first seen (a 90 ms freeze for Cheese Cube's glowing weapon props, 101 ms on Kino's first played frame). Now, with the animation loop paused:
  1. a `later` group goes in front of the camera: `mods.warmObjects` (mods push objects that only appear later; the fx mod pushes one pooled sprite), every power-up model with its aura sprite, and the enemy templates (`enemies.templates/heads/dog/quad/quadHead`; clones share their materials);
  2. `mods.emit('warm')`: mods apply pending material changes (the lighting mod's `tagShadows` sweep normally only runs in play, so meshes added after its setup changed program on the first played frame: LIGHT_CLAMP define + baked-light patch);
  3. one frame with shadow maps forced to redraw (their depth programs), through a spy on `renderer.render` that records each scene's render target;
  4. every hidden non-light object is made visible and each scene is `compileAsync`ed against its own target (no texture uploads, so hidden weapons don't fill VRAM), then hidden again;
  5. the held gun's textures are uploaded (`initTexture`, only those);
  6. every program's `getUniforms()/getAttributes()` is called: without KHR_parallel_shader_compile (absent on the host) compileAsync only queues the compiles and the driver blocks on first use, which had become a 360 ms first played frame.
  It runs again 1.5 s and 4 s after loading while the game hasn't started (cheap: built programs are reused). Cost: Cheese Cube 10 programs / ~100-180 ms, Kino 4-5 programs / 270-600 ms; ~150-300 MB more VRAM on Kino (the templates' textures).
- Results: Cheese Cube 0 mid-game compiles (was 3 incl. the 90 ms one), steady 60 FPS with ~1.4 ms update / ~3.5 ms render. Kino: 0 mid-game compiles (was 12), hitches over 50 ms in 45 s 14 → 5. What's left on the first played frames is GPU-side (driver pipeline creation on first draw, cached by the NVIDIA driver between runs) and doesn't show in our CPU timings.
- `perf-diag.js` now reports shader programs compiled during play (names per window, a session count), shown by perf-report.
- Testing gotcha: another session's headless Chromium on the same 6 GB GPU can make runs lose the WebGL context (Kino peaks ~4.5 GB alone). The scratchpad scripts detect `webglcontextlost` and retry; treat a lost run as invalid.

## Der Eisendrache frame-rate pass 2 (2026-10-17, user: "a clean 120 fps on DE for the 4070 ti super ... make the game run more off gpu")

The user's play-time logs that evening (Ultra, 2560x1369, Rind 0.3.4): 52 FPS average, 6.6 ms of game update and 11.2 ms of render CPU a frame, so the frame was CPU-bound on both halves. Measured here with a castle-wide benchmark (spawn x4 yaws, every perk machine and the power switch from two sides, the Pack-a-Punch, the undercroft; `RS=0.5` so the GTX 1660 Ti is out of the picture; the host was shared with another session's browser, so compare back to back): average 35.8 -> 58.5 FPS, worst view 17.2 -> 38.7. A CDP profile of the baseline put 12% of the CPU in three's `updateMatrixWorld`, 8.6% in `projectObject` (the renderer's object walk), 13% in the player's capsule collision, 27% in `setProgram` (per-draw uniforms) and 2% in the castle mod's instance sync. What it was:
- **The scene walk.** static-freeze v1 froze the objects but not the scene root, and three's `updateMatrixWorld` recomposes every `matrixAutoUpdate` object and then forces its whole subtree: the root forced all 6,500 objects every frame, so the freeze had gained nothing. `static-freeze.js` now covers the whole scene (Der Eisendrache's doors, placed props, booths and rigs sit beside `world.root`), stops composing the root's matrix, freezes bones too (still rigs), gives every all-static subtree an `updateMatrixWorld` that returns unless forced or flagged (the walk stops there), compares half the snapshots a frame (a moved object thaws within two frames; `updateMatrix()` + `updateMatrixWorld(true)` is immediate), and reopens a chain when something under it thaws or a child is added. `hideBones` (still-skeletons.js): bones with nothing but bones under them are `visible = false`, which prunes the renderer's walk (1,036 on the castle) without touching the animation; `Bone.add/attach` re-show the chain (a held weapon on a hand).
- **The instance sync** (merge-props.js) compared the matrices' doubles against a Float32 copy, so every instance was re-set and its buffer re-uploaded every frame; and it walked each piece's parent chain for visibility (780 pieces). Float64 now, visibility per parent per frame, and the originals leave the scene graph (each instance follows its parent node's matrix times its own local one, so a slid door piece still follows).
- **Draws**: the gondola cars' pieces merged per node and material (TRAM was excluded: 246 draws), door pieces merged per material and slide (custom-world `mergeDoorPieces`, ~90 draws), the booths' LEDs, wires, glass and coolant hidden past 900 units (~35 draws a booth), transparent materials and materials whose image texture-memory had already released allowed into the texture arrays (instance-cull `hasImage`, blend-state keys, transparent array batches grouped across the overlay layers' render orders).
- **Player collision** (collision-world.js): the capsule was tested 4-8 times a physics step against the whole 6.5M-triangle BVH. `_gather` collects the triangles in a padded box round the capsule once (with their bounds for a cheap reject) and the tests reuse them while the capsule stays in the box; `invalidateCache()` after the booths clear debris. The bvh functions left the profile's top 30.
- `hud()` writes a DOM text only when it changed (every assignment invalidated layout: ~1%).
- A/B switches: `?noFreeze` (freeze + hidden bones), `?noMergeProps`, `?noArrays`.
Left on the CPU: per-draw uniform uploads in three (`setProgram` and friends, now the largest share), the renderer's walk over the remaining ~2,500 objects, and the lighting mod's post chain.
- **Idle-machine confirmation (2026-10-18 02:50 UTC, load 3)**: the same castle benchmark with everything above: average 74.2 FPS (13.5 ms), worst view (the spawn looking over the castle) 54.4, best 122; load 94 s. Kino at the same settings: 109 FPS average, worst view 72. The 58.5 above was measured with another session's browser and builds sharing the host.

## First-draw stalls (2026-10-24, user: "alot of freezes ... when shooting the gun"; RTX 4070 Ti Super, Rind 0.7.1, ANGLE D3D11, Ultra)
- The user's play logs showed 2-4.5 s frames where update and render stayed under ~20 ms and often no long task ran: the main thread was waiting on the GPU process. Most fell in the first ~30 s of play. On D3D11, ANGLE builds the real pipeline on the *first draw* of a program with a given vertex layout and render-target format, not at `compileAsync`, so the old warm-up (compile + `getUniforms` for hidden objects) left those builds for play.
- **Warm draw** (`warmShaders()` in engine.js, after the compile loop, while the hidden objects are still shown): frustum culling is turned off for one draw of every warm target (scene and view scene), so everything in the map draws once at load. Hidden objects' textures that aren't uploaded yet are swapped for 1x1 stand-ins for that one draw (in this three build a 2D map swap keeps the program; `envMap` is left alone because it does change it), so the warm draw doesn't fill VRAM. Kino: 33 program/layout/target pairs, ~100 textures stood in, 200-250 ms (the compile step after it gets faster by about as much; whole loads varied 22-34 s either way on the host, vulkan). `?noWarmDraw` turns it off for A/B tests.
- **First-draw tracker** (`firstDraw` in engine.js, wraps `renderer.renderBufferDirect`): counts program x vertex layout x render-target format pairs drawn for the first time. Perf lines carry `fd` (per window and per session), and each hitch's extra is `[first draws in the frame before, in the hitch frame, first material names]` (`perf-report.mjs` prints both). A hitch with first draws is a pipeline build; one without is something else.
- Test: `kino` scripted play (spawn + each exfil zone, 4 directions, 6 shots and a reload each): with `?noWarmDraw` 1 first draw during play, with the warm draw 0.
- What `perf-report` still lists as compiled mid-game on Kino: 3 `physical` LIGHT_CLAMP programs from hd-weapons' wall-gun preload (`compileAsync` when you walk near a wall buy, in the background, by design: the wall guns' materials get the lighting setup from their wall displays after the load-time batch). Keeping the load-time batch hidden in the weapon scene for the warm-up didn't catch them and made the warm draw 2 s (1,500 textures stood in), so it was dropped. `programCount` is now resynced at the end of each warm-up, so programs compiled while loading are no longer counted as mid-game.
