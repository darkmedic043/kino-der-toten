# Map materials and HD textures

- **Kino map materials** (`mods/map-materials`, Kino only): normal maps: the export attached none, but 400+ ship in `textures/` in DXT5nm layout (X in alpha, Y in green). `.tools/build-kino-normals.py` converts the matched ones to standard RGB normal maps in `textures/nrm/*.webp` (236 files, 7.6 MB) and writes `normals.json` (material name → map); the mod loads them after start with normalScale (1, −1) and max anisotropy on colour maps. The theatre chandelier's opaque slot also holds bead and crystal cards, so an `onBeforeCompile` discard cuts alpha < .45 only where fract(uv.x) < .49 (the frame half has zero alpha too). the map export lost blend modes. Glass (`global_glass*`, `dec_glass01`, lightning chamber glass, plus model glass like `mtl_glass_v2_off`) was a 0.45 alpha cut-out, so clear panes vanished and frosted ones went solid; it is now alpha-blended with depthWrite off. Dark-on-white stains (burntstain, darkstain, grime, scorch, pipe stain, blast crater) use MultiplyBlending with polygon offset; soft decals (blood, cracks, puddles, `*_blend`) blend instead of cutting at 0.45. `hdrportal_lighten` (an editor light portal) is hidden and `clothcable_glow` is additive. Layered `base:decal` materials (names containing ':') are left alone. It also caps the spawn-room return teleporter pad (centre 2,1274; its collision is a bowl from rim ~89–92 down to ~78) with an invisible 57-radius cylinder collider (top 89.4) pushed onto `world.dynamic`.
- **HD textures** (`.tools/upscale-kino-textures.py`, Real-ESRGAN ncnn-vulkan x4plus in `~/.local/opt/realesrgan`, runs on the GTX 1660 Ti at about 20 s per 512² texture): the 376 Kino colour textures of 128–512 px are padded with a wrapped border (for seamless tiling), upscaled ×4, cropped, and Lanczos-resized to ×2 as `textures/hd/*.webp` (42 MB). `hd.json` maps file → HD and `hd-materials.json` maps material name → HD (415 materials; rebuild with `--table-only`). The map-materials mod swaps them in one per frame after start (ImageBitmapLoader, off-thread decode) and disposes the SD GPU copy; Settings → HD textures toggles live, and phones keep the SD textures.
- **Smooth shading** (map-materials): the Kino export (compose_scene_t5.py `build_prim`) writes flat per-triangle normals. At load, vertices at the same quantised position (1/20 unit) get the area-weighted normal of the faces within 50° of their own face (in place, 917 meshes in about 0.7 s).
- **HD weapon textures** (`mods/hd-weapons`, `.tools/upscale-kino-textures.py --weapons`): 108 textures referenced by every weapon glTF (game-data plus Moon: model, worldModel, leftModel, upgrades; 128–512 px sources; the 46 2048 px upscales of 1024 px originals were dropped 2026-10-16 for video memory, see performance.md), upscaled the same way into `textures/hd-weapons/` (44 MB; names are path-unique with `/` → `__`). `hd.json` maps the web-root-relative source → HD. `prepare()` installs a URL modifier on the shared `assetManager` (runtime-assets.js), so every weapon load (viewmodels, world models, box) gets HD while `settings.hdTextures` is on; phones skip it.
- **KTX2 textures** (2026-10-17, `ktx2.js`, `.tools/build-ktx2.mjs`): GPU-compressed copies of every power-of-two image under `textures/` (2,940: the Kino map, all weapon/character/zombie models via `../textures/...`, `textures/hd`, `hd-weapons`, `nrm`), in `export/web/ktx2/<path>.ktx2` (git-ignored, ~570 MB; derived from ripped textures, so streamed, never in Rind's install) with `ktx2/manifest.json` (`path → [stamp, w, h, bytes]`; the stamp goes on the URL as `?v=`).
  - Encoding: KTX-Software 4.4.2 (`~/.local/opt/ktx-software`, official release, `LD_LIBRARY_PATH=lib`; `KTX_HOME` overrides), UASTC quality 2, RDO λ 1.0, zstd 18, full mip chain, RGBA; about 30 min for all on 6 cores, incremental afterwards. **Rerun `node .tools/build-ktx2.mjs [roots]` after changing or adding textures**, or the game keeps serving the old copy. Sources go through ffmpeg to plain RGBA PNG first: most BO1 PNGs carry `gAMA 1.0`, which Chromium's glTF path ignores but `ktx create` honours (it brightened them: PSNR 12 dB); the transfer function is *assigned* (`--assign-tf`), never converted, because three picks the sRGB or UNORM BC7 upload format from `texture.colorSpace` per material slot. `_n`/`_nml`/`_nrm`/`nrm/` files are tagged linear.
  - Quality: UASTC 46-56 dB against the source (ETC1S was 33-40 dB); screenshots against the image path 52-57 dB (gun close-up, Cheese Cube) and matching Kino views. Desktop GPUs get BC7 (`EXT_texture_compression_bptc`).
  - Runtime (`setupKtx2(renderer)` in engine.js; desktop only, phones keep their -mobile handler; `?noKtx2` turns it off): an `assetManager` handler for png/webp/jpg answers every glTF image request (after `assetManager.resolveURL`, so the hd-weapons redirect still applies): listed → `KTX2Loader` (own LoadingManager, transcoder `vendor/jsm/libs/basis/`, 4 workers), one transcode per file shared by clones (Kino: 1,198 files for 1,658 uses); not listed or failed → an `ImageBitmapLoader` texture exactly as GLTFLoader makes it. Textures come back with colour space none like an image texture; GLTFLoader sets sRGB on colour slots. `ktx2Texture(url)` does the same for code that loads its own textures (map-materials' normal maps and HD swaps; HD swaps skip `generateMipmaps` for compressed textures). `kino.debug.ktx2()` has counts.
  - Also encoded (same day, later): `mods/maps/der-eisendrache/tex` and `mods/maps/the-giant/tex` (3,774 WebP, 128 MB → 503 MB of KTX2, 27 min). Der Eisendrache VRAM 4.57 → 2.03 GB, load 83 → 76 s; its texture arrays are now compressed at native size (they were RGBA resized to 256 px). See performance.md (frame rate pass) for the batching.
  - Not covered yet: maps with their own loaders (Moon, Ascension, Shangri-La, Call of the Dead, Coast), embedded glb images (Cheese Cube), TextureLoader paths (fx, characters, camos), phones (ASTC/ETC2 would help them most), non-power-of-two images.
  - Measured on Kino (GTX 1660 Ti, desktop): VRAM 3.42 → 1.21 GB; renderer + GPU process RAM 4.54 → 3.57 GB (no decoded bitmaps; but the JS heap grows 0.6 → 1.2 GB because the transcoded mips stay in RAM after upload: freeing them, with a restore path like texture-memory.js, is a follow-up); load 23 s either way locally; FPS unchanged; downloads 213 MB / 1,531 requests → 234 MB / 1,039 (PNG sources shrink about 2x, WebP sources grow 3-7x: they are heavily lossy). `.ktx2` isn't in Cloudflare's default cached extensions, so those come from the origin through the tunnel unless a cache rule covers `/ktx2/`.

## Der Eisendrache: grey sheets, carved decals, the pink road (2026-11-12, user: "white blotched like this around the map")

`mods/der-eisendrache/carved.js` (`carvedDecals(root, scene)`, called in the mod's setup before the props are merged) fixes three export defects at load, without a map rebuild:

- **Duplicate rune circles.** The rune prison quest's glowing circles are placed twice by the build: `CASTLE_BQ_rcircle_*` (hidden, the bow quest shows them) and plain script models `CASTLE_SM_aq_rp_runic_circle_{road,roof,rampart}` that nothing hid. The model has no colour image, so each was a 232 unit flat grey sheet (white under the outdoor light). The `SM` copies are removed from the scene. Their flat triangles stay in `COL_scriptmodels` (level with the ground, harmless).
- **"Carved" decals.** BO3 materials named `*_carved` with only a normal map (the rune circles and symbols cut into the ground, the wind runes on five walls as props and BSP, the pyramid's celestial carving) bend the normals of the surface under them. The build wrote them opaque `[.3,.3,.3]`. They become overlays: a canvas texture made from the normal map's slope (alpha = smoothstep of `hypot(nx, ny)` from .08 to .44, dark stone colour), `transparent`, no depth write, polygon offset, `renderOrder` 2100. Read from `normalMap.image` at setup (before the engine releases decoded images); with no readable normal map the material is hidden. Materials that have a colour image (`keepers_stone_carved`, the clock symbols) and the alpha-0 flagstone decal are left alone.
- **Blood footprints.** `wc/t7_decal_blood_footprints` (24,600 triangles over the lower road) lost its footprint image, so the build drew its red tint over a micro detail map: a pink wash over the snow. Hidden while its colour image is a `_micro_` one.

How it was found: `scratch/blotch/ray.mjs x z` (a vertical ray through the map GLB, every triangle crossed with node and material) named the sheet; `near.mjs` lists a region. A build-side fix (skip the `SM` duplicates, export carved materials as overlays) can replace this file after the next rebuild; the function then finds nothing to do.

## Der Eisendrache: overlay layers drawn solid (2026-11-12, user: "also noticing stuff like this")

The map build marks a material as an overlay only when its *name* says `decal` or `_blend`, and it merges equal materials under whichever name came first, so many overlay shells on props came out opaque: white snow coats over whole machines (the Pack-a-Punch roof's generator, boxes, tesla towers), a pale grey panel where a chalkboard's writing is, purple-grey slush sheets, solid cards where chains, grates and banners have holes. `mods/der-eisendrache/overlays.js` (`overlayLayers(root)`, called right after `carvedDecals`, before the props are merged; `?noOverlays` skips it) sorts opaque materials by their colour texture's stem (the GLB material name is unreliable) into four kinds:

- **blend** (85 stems: every `decal` texture plus chalk writing, labels, stains, rivet and weld strips, slush, rune and logo cards): transparent, no depth write, polygon offset -1/-8, render order 2200. Carved symbols and normal-only weld seams (white image) are tinted to .22.
- **mask** (26 stems: chains, grates, straw, splinters, fletchings, banners, vista cards): `alphaTest = .4`.
- **snow** (materials named `snow*_blend`, not the BSP `wc/` ones, which carry real blend weights): transparent with a vertex alpha written from the world normal (0 below .2 up, full above .75), since Greyhound's prop vertex colours are all 255: snow stays on top faces only. An instanced prop uses its first instance's turn.
- **soft** (the oxidised copper shell .35, dark grout .5): a constant opacity over the base they duplicate.

Left solid on purpose (their alpha is data, not coverage): the blue barrel, icicles, `t7_micro_stone_mixed*`, opus tile, tritium, jars, the crates' `_wood_blend`/`_metal_blend`. The lists come from the textures' alpha statistics and two contact sheets (session scripts); a rebuilt map should mark these in the builder instead. Checked on the GPU in cropped copies of the map (bedroom chalkboard, Pack-a-Punch roof); the whole map cannot be run headless within the memory rule (renderer 2.8 GB while loading, 2.36 GB even with a cropped map file), so the in-engine wiring is covered only by syntax checks and the sandbox warm-check.

## Metal look on the BO3 ports (2026-11-12)
BO3 keeps a metal's colour in its specular map and leaves the diffuse black. The map export has neither the specular maps nor reflections, so pipes, ducts, gratings, cabinets, lamp housings and brass were flat near-black shapes (The Giant: 137 materials, Der Eisendrache: 465). `metalLook(world.root)` (`mods/lighting/metal-look.js`, called in both map mods' setup, before the warm-up) gives every untextured material whose name reads as metal (`IS_METAL`, minus `NOT_METAL`) a colour, roughness and metalness by kind (`KINDS`: rust, brass, copper, painted, plain steel...; first match wins); its normal map does the rest. It is a stand-in: the real fix is exporting the specular/gloss images in `build_bo3_map.py` and rebuilding both maps, which has not been done.

## Map detail pass: tiled micro maps and larger copies (2026-11-12)

User: "some textures are also extremely blurry on de". Two causes, measured by `.tools/map-detail.mjs` (texels per world unit of every colour map, weighted by the area near walkable points):

- **Stretched detail maps.** BO3 props take their colour from small tiling maps (`i_t7_micro_*`, and library maps such as `i_t7_sand_pebbles_fine`); the port's materials only carry the semodel's `diffuse` name, so each was stretched once over the whole prop (a boulder: 256 texels across 1,000 units). The fix is free: `applyDetail(root)` (`map-detail.js`) gives the material's colour map a repeat so one tile covers about 32 units. The texture is a clone that shares the image (`Source`), so nothing more is uploaded, and the normal map keeps its own UVs. Micro maps are tiled from 2 repeats up (capped at 32); other library maps only on prop materials (`mtl_*`) and only between 2.3 and 8.5 repeats: past that the prop is using one flat patch of the texture as a colour, and world (bsp) materials have real UVs and are never tiled.
- **Small copies.** The other colour maps under 4 texels a unit, largest blurry area first, are re-encoded at 512 or 1024 from the Greyhound export within a budget (`--budget`, default 160 MB of texture memory) and swapped in at load by a URL redirect: `prepareDetail(dir)` chains `assetManager.setURLModifier`, like the HD weapon textures. It is skipped on phones, on Low graphics and with HD textures off; the tiling applies everywhere.

Both lists are in the map's `detail.json`, next to the GLB (git-ignored, like the textures): `{tile: {material: repeat}, hd: {old uri: new uri}}`. Der Eisendrache: 328 materials tiled, 88 larger copies, about 109 MB more texture memory. Its mod calls `prepareDetail` from the mod script's `prepare()` (before the map loads) and `applyDetail(world.root)` in `setupLook`; `?noDetail` turns the redirect off. The Pack-a-Punch model is a separate file: its rocks get a repeat of 3 in `setupPap`.

Rerun after a map rebuild: `node .tools/map-detail.mjs der-eisendrache --pts <walkable points json> --go` (the points come from the collision audit's flood; without `--pts` every surface counts; no `--go` = report only). Checked in the cropped rocket-pad scene only (renderer 540-590 MB with or without it).

**The Giant (2026-11-19, user: "clean up the maps with more ehish textures").** Same pass: 83 materials tiled (the teleporters, the furnace, generators, pipes, the bridge, snow chunks), 4 larger copies (the robot torso, a rubble pile, the boxcar, the torn flag; about 14 MB). Its mod has the same `prepare()` and `applyDetail(world.root)` after `metalLook`. The map was already at 512 px arrays, so the gain is on props, not walls. Walkable points for `--pts`: `node .tools/col-audit.mjs <id> --flood-only --points raw.json`, then wrap the list as `{"pts": [...]}`.

## Larger copies of embedded textures: the World at War ports (2026-11-19)

`build_waw_map.py` embeds every texture in the map's GLB at 512 px at most, so the detail pass's URL redirect can't reach them. `.tools/map-hd.mjs <map-id> --src <dump images dir> [--pts walkable.json] [--budget 96] [--upscale [--up-budget 64]] [--go]` measures texels per unit near the walkable points for each embedded image and writes larger copies of the blurry ones (under 4 texels a unit over at least 1e5 square units) to `mods/maps/<id>/hd/<image>.webp`, with the table `hd.json` (`{image name: file}`; both git-ignored, ripped):

- **Larger originals.** Where the zone dump has the image at 1024 or 2048, it is re-encoded from there (x2, or x4 when x2 stays under 3.5 texels a unit).
- **`--upscale`.** Most WaW originals are 256 or 512 px, so there is nothing larger. Those under 2.5 texels a unit over 2e5 square units are upscaled to twice their size with Real-ESRGAN (`~/.local/opt/realesrgan`, on the GPU: don't run it during a game test), with a wrapped border so tiling textures stay seamless, as `.tools/upscale-kino-textures.py` does for Kino. An image with almost no UV area (under .2 texels a unit: a flat colour patch) is left alone.

Counts: Nuketown 13 originals + 8 upscaled (about 25 MB of texture memory), Malibu Drive 45 + 24 (about 76 MB), Cheese Cube 1. After `--go`: `LD_LIBRARY_PATH=~/.local/opt/ktx-software/lib node .tools/build-ktx2.mjs mods/maps/<id>/hd` (a 2048 px image takes about 100 s to encode; without the KTX2 copy the WebP is loaded instead and costs four times the memory).

At load, a map entry with `"hd": true` makes `CustomWorld` call `embeddedHd(root, dir)` (`map-detail.js`) right after the GLB is parsed and before anything is merged or batched: it finds the materials whose `map`/`emissiveMap` texture is named in `hd.json` (GLTFLoader names a texture after its image), loads the copy (`ktx2Texture(url)`, else `TextureLoader`), copies wrap, repeat, colour space and UV channel from the embedded texture and disposes the embedded one. Same switches as the redirects: skipped on phones, on Low graphics, with HD textures off and with `?noDetail`. No map rebuild and no `?v=` bump are needed; after a rebuild rerun the tool (image names stay the same unless the map's texture list changed).

## Gorod Krovi: the clean-up pass (2026-11-22, user: "do some clean up on gorod krovi to make it look beautiful")

`tidy(root)` in `mods/gorod-krovi/look.js` (runs first in `setupLook`, before the engine batches the map; counts in `look.report.tidy`, now wood 144, brick 7, paint 7, blood 14, wallpaper 10). It corrects colours the map build guessed from material names. No map rebuild.

**Why the colours were wrong.** A material whose colour map is a BO3 "micro" detail map (or a constant) gets a tint by name in `build_bo3_map.py` (`PAINT` first, then `TINTS`), divided by the detail map's brightness and clipped at 1 per channel. Three ways that goes wrong:
- The detail map has a colour of its own. The wood ones are orange already (`wood_worn_varnished_01` averages sRGB 100,67,31), so a brown tint on top gave bright orange wood, and a grey "drk" tint gave orange-red oak panels.
- The name matches the wrong word: "red" in `brick_worn_red_lt` made loose bricks ketchup-red cubes, "rustic" wood matched `rust`, and blood decals (white images) became bright red paint.
- The clip at 1 changes the hue: yellow (.62,.5,.1) over a dark detail map became (1,1,.27), lime.

**The fix: colour x detail-map average = a target.** `MICRO` holds the sRGB average of each detail colour map (ffmpeg, `scale=1:1:flags=area` over the map's `tex/`); `over(target, avg)` returns target / average in linear, scaled down as a whole when a channel passes 1 (the hue stays, the surface is a little darker). Targets come from the map's own photographed textures: raw wood (112,96,80), furniture wood (98,72,52), dark wood (72,52,38), red-painted wood (100,54,44), bricks (135,100,86) and (97,73,63). Paints clipped off their hue get the builder's own paint colour through `over()`. Blood is (.06,.005,.005) at roughness .28. A material with a real colour map is never touched.

**Wallpapers.** Two separate faults:
- BO3's colour variants of one wallpaper (`_red`, `_blue`, `_green`) share their images and differ by a tint the export lacks. The builder merges materials with the same images (`mat_sig`), so the variant survives only in the **mesh** name: `tidy` clones the material per variant and tints it (`WALL_TINT` over `WALL_AVG`). The clones still share one static batch (the batch colour is per instance).
- Patterns 05 and 06 keep their print in the colour map's alpha. Built as cut-outs, the flowers were holes in the wall. `inkPattern` draws them opaque and darkens the wall where the alpha is low (`WALL_INK`), in a shader patch appended after `#include <map_fragment>`. It survives batching because `arrayMaterial` chains the base's `onBeforeCompile` and `arrayKey` includes `customProgramCacheKey()` (the patch adds `|ink<value>` to it); a patch that *replaces* that include would be lost.

**Looked at and left alone:** the lime object hanging in the power room is a comm monitor's green screen (a real texture); the red floor by the factory street is rubble under the map's own baked firelight; the orange at Quick Revive and the MPL is firelight on real textures.

**Checked with** the look harness (`scratch/gklight/look2.mjs`, `LOOK=` a scratch copy, 256 px textures, no sun shadows or fires: before/after of the same shots plus the 32-marker sheet, 0 errors) and a light-copy match with the module routed in (`.tools/map-test.mjs`, `ROUTE=`): 0 errors, the wallpaper batches opaque, 4 more programs at load and none more in play than before. For another port: list name-tinted materials by saturation and usage, measure the detail maps, and write targets rather than new name rules.
