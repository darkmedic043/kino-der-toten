# Co-op multiplayer

- **Co-op** (`mods/multiplayer`, `net.js`, server rooms): the server has a dependency-free RFC6455 WebSocket at `/api/ws` (upgrade handler, masked client frames, 25 s pings) and rooms of 4-letter codes, max 4, where the creator is host and the room closes when the host leaves; `GET /api/rooms/<code>` returns `{page, map, players}` for join-by-code. Relay protocol: `{t:'to',target:'host'|'all'|id,data}` becomes `{t:'msg',from,data}`. Game protocol: `pose` (all, 15 Hz), `snap` (host, 12 Hz: round, phase, doors, power, boards, zombies `[id,kind,x,y,z,yaw,state,hp,speed]`, and a `gid` that changes on host reset), `dmg` (client→host) answered by `res` (points/XP applied on the client), `hit` (host→victim), `world` (client doors/power), `ended`. The host sets `enemies.targetFor` (nearest player, sticky ×1.3) and wraps `enemies.onDamage(amount,z,victim)`; the `enemies.js` upstream edit adds the `targetFor` hook plus `victim` args. Clients replace `enemies.update`/`hurt`/`nuke` with a mirror. `host.remoteDamage` suppresses host XP and hitmarkers for teammates' hits (`kill` event `remote` flag). URL: `?mp=host` creates, `?room=CODE` joins (history rewrites to `?room=`). Stage 3: power-ups are host-authoritative (host ids `nid`, the snap `pu` list, `pu` collect broadcast calls `kino.debug.collectPowerup` everywhere, and the host also grabs for remotes within 70); the box location is in the snap `box` (client teddy moves are sent as `box`); custom-trap activations are broadcast as `trap`; Kino trap kills already propagate through `dmg`. Stage 4: in co-op, a lethal hit without QR is intercepted (`session.damage` wrapper) and becomes DOWN (phase `reviving`, reviveLeft ∞, perks cleared, 30 s bleed-out, camera lowered and rolled); teammates hold F (tracked via KeyF/KeyE) within 90 for 3 s and send `revive`; bled-out players are DEAD and spectate via `host.camera`, respawning on `roundEnd`; everyone down gives the host `gameover` broadcast and `forceGameOver()`. The snap phase maps the host's personal `reviving` to `fighting`. Host migration: the server reassigns the host on leave (`left` carries `host`) and the new host calls `becomeHost(true)` (restores the original enemies/powerups functions; mirrored zombies keep their host ids because clients set `z.id=netId`). A Worker-driven 20 Hz ticker keeps the host simulating while paused or hidden. The HUD label switches from SOLO to CO-OP.
- **Co-op lobby** (multiplayer mod): the #start click is blocked (capture phase) until `lobby.go`. Players send `{t:'ready'}` to the host once `getState().ready`; the host keeps the set and broadcasts `{t:'lobby',ready,started}`. The host's START GAME is enabled when every player in `net.players` is ready and starts everyone; others then get "click to join in" (pointer lock needs a click), and late joiners go straight in once ready. Verified with two browsers.
- **Skins in co-op (2026-10-05)**: create/join also send `variants` (the profile's customisation picks for the equipped character, `profile.variants[character]`); kino-server keeps them per player (`cleanVariants`: at most 32 string pairs, 32 chars each) and includes them in the player list; `addRemote` builds the teammate's model with `entry.choice` = those picks. Before, teammates saw the right skin (e.g. Bondrewd Premium) but its default options (no Blessing, Science outfit). Picks changed during a game are not resent (they apply on the next join).
- **Respawn beside a teammate (2026-10-05)**: at a new round a dead/downed player comes back on walkable ground about 45 units from a standing teammate (`world.closest`, within 40 in height), else at the map spawn. On Cheese Cube the spawn is under the rising cheese, so respawning there killed you at once. Verified: guest respawned at (117,840,0) beside the host at (72,841,0).
- **Crawl when downed (2026-10-05, engine.js)**: while `phase==='reviving'` the player gets the move keys scaled to about 40 units/s with crouch held (was no input at all). Measured: 120 units in 3 s, still downed. Also applies to Quick Revive's solo self-revive.
- **Lobby menu (2026-10-05, user: "more like a popup than a proper menu"):** `#coop-lobby` is a full-screen menu in the game menu's style.
  - **Left:** map title, room code, START GAME (host; enabled once everyone is loaded), JOIN THE GAME or a waiting note (guests), COPY INVITE and MAIN MENU.
  - **Right:** SQUAD n/4 cards (initial, name, HOST/YOU, operator · class · level, a loading bar). Their state reads LOADING n%, READY or IN GAME; empty slots say OPEN SLOT.
  - **Messages:** players send `{t:'linfo', p, op, cls, lvl, in}` to the host each second while loading, on ready and on start. The host keeps `lobby.info` and broadcasts it in `lobby`.
  - **Start for everyone:** a guest that's loaded enters on the host's started flag via `enter(false)`. It runs `kino.debug.resume()`, so the game starts at once, and shows "THE GAME HAS STARTED · CLICK TO PLAY" until the first click, which captures the mouse (pointer lock needs a gesture). A guest still loading enters as soon as it's ready.
  - Tested with two browsers: the guest went in when the host started.
- **Friends (2026-10-05):** a signed-in (Discord) friends system.
  - **Server** (`.tools/kino-server.mjs`):
    - `social.json` in the data dir holds users {name, username, picture, pid, seen}, friends, and requests {to: [from]}.
    - Players are addressed by `pid`, a 12-character hash of their account, so Discord ids stay on the server. Sign-in now also stores the Discord `username`; older sessions get it on their next sign-in.
    - API: `GET /api/social` gives {me, friends, incoming, outgoing}, each with a status. POST `/api/social/request` takes {name} (pid, username or display name; display names only when unique) or {id}. A request to someone who already asked you makes you friends. Also POST `accept`, `decline`, `cancel`, `remove` and `invite` {id, room, map} (friends only, online only, the room must exist).
    - Presence: a social WebSocket `/api/social/ws` (signed-in only; menu and game pages). Clients send {t:'status', status:'menu'|'game'|'launcher', map, mapName, room}; the server pushes `presence`, `request`, `friends` and `invite` to friends. Status reads offline (with last seen), online (with `where`: 'menu', or 'launcher' when only the Rind desktop launcher is open, shown as "Online · in Rind"), or game (map, co-op room, players, joinable); room joins and leaves update it.
    - Room players carry `uid` (their pid) so lobbies can offer ADD FRIEND.
  - **Client** (`social.js`): `startSocial`, `setStatus`, `onSocial`, the request/accept/… calls and `statusText`. Friend requests (ACCEPT/DECLINE) and game invites (JOIN/LATER) show as notifications in the top right on any page.
    - Main menu: a SOCIAL tab with a request badge on the nav. It lists friends sorted in game / online / offline with a status dot, JOIN when their co-op room has space, and remove. It also shows your card (@username, friend ID, COPY), ADD FRIEND by username, name or ID, and incoming and sent requests.
    - Game: `mods/social` reports In game with the map and co-op room every 2 s on change. The co-op lobby has + ADD FRIEND on signed-in players (or FRIEND / REQUESTED) and an INVITE FRIENDS list (online first, INVITE, then SENT).
  - Tested with a throwaway server (`KINO_DATA` in the scratchpad, port 5199) and two made-up sessions: request by username, then the notification and ACCEPT; status online, then in game (co-op 1/4, JOIN); lobby INVITE gave a JOIN notification that opened the room.
- **Lobby avatars (2026-10-05):** room players carry `picture` (their Discord avatar, signed in); lobby cards show it round, falling back to the name's initial.
- **Der Eisendrache in co-op (2026-10-17, user: "make it co op compliant please")**: everything the map adds runs on `mods/der-eisendrache/sync.js` (`kino.castle.sync`), over the multiplayer mod's relay:
  - `act(type, data)`: an ordered event. The host applies it, numbers it and sends `cev` to everyone (guests ask with `creq`); handlers get `ctx = {by, mine, host, rand}` (`rand` seeded by the host, the same on every client). The host keeps the game's log; a guest asks for it (`clogreq`/`clog`) once set up and again 400 ms after a reset (its own reset can land after the host's first new-game events).
  - `shared(key, get, set)`: host-owned state sent 5 times a second (`cst`): gondola, low gravity clock, the rocket schedule, the clock tower, the boss, Skadi.
  - `fx(type, data)` / `onFx`: passing effects (the bows' elements), sent straight to everyone (`cfx`), not logged (a late joiner doesn't replay them).
  - `hurt(z, amount, ctx)`: damage on the host only (its zombies are the real ones), credited to `ctx.by` through the multiplayer mod's `res`. `hitPlayer(id, amount)` uses `hit`. The multiplayer mod's `dmg` now sets `host.remoteBy` (the teammate who hit) next to `host.remoteDamage`.
  - Kills: the host relays its zombies' deaths as `kill` events `{p, kind, melee, head, by, bp, crawler}` (`bp`: where the killer stood), after the frame's other kill listeners (queueMicrotask).
  - Per system: gondola (host phases, fuse/call events), pads, Pack-a-Punch, rocket-pad flag, dog rounds (host), dragons (sync kills; one bow per player), Panzer (host spawns, guests mirror through an `enemies.spawn` wrapper), Wunderfizz, traps (host kills), craftables (host picks spots; shield and nitrous stay personal), low gravity, the Easter egg and the Keeper boss (guests mirror it), side eggs, and the bow quests (ownership per player, see waw-ports.md).
- **Malibu Drive in co-op (2026-10-18)**: the map's quests, Tony's armors and the heroes' powers run on Der Eisendrache's `sync.js` too (waw-ports.md, Malibu Drive, Co-op).
- **Split screen (2026-10-19, user: "add split screen into melon zombies, allowing for 2 different accounts to play on the same pc")**: run by the Rind launcher (`~/projects/rind` src/split.js, its CLAUDE.md "Split screen"): one window, two copies of the site, one per Discord account (each in its own Electron session, so cookies and local storage are separate), playing as an ordinary co-op room. Rind rewrites a map launch to `mp=host` (or into the other half's room) and brings the other half into the room when the address gets `?room=`. Nothing server-side changed.
  - Each copy gets `window.rindSeat` (`{seat, players, keyboard, pad, name}`) from Rind's preload. `export/web/seat.js` reads it: `seatPad()` is this player's controller (`pad` indexes the connected controllers in `getGamepads()` order; null = none; outside split screen the first connected pad, as before), used by `mods/controller` and `gamepad-nav.js` (the main menu). A controller-only seat doesn't pause on window `blur` (engine.js's blur handler checks `padOnly()`; that half never keeps focus). A capturing `blur` listener added by a module can't do it: on `window` Chromium runs the listeners in registration order, capture or not, so the engine's own ran first. A tag "P1 · NAME · KEYBOARD & MOUSE" / "P2 · NAME · CONTROLLER 1" shows for 6 s at load and when Rind swaps the controllers (F8).
  - Lobby with a controller (any controller player, not only split screen): `mods/controller` navigates `#coop-lobby` while it is open (initial: START GAME / JOIN THE GAME when enabled), Start presses that button, and neither Start nor Cross resumes past the lobby any more (they used to start the game before the host did). `enter()` in the multiplayer mod resumes a controller player (`padOnly()` or `body.using-pad`) without the pointer-lock click and without the "CLICK TO PLAY" hint.
  - No WebHID DualSense link in split screen (`showLinkButton` is false with a seat): it can't tell which DualSense is whose. Rumble through the Gamepad API still goes to each player's own pad.
  - Both copies play their own sound (music and announcer twice, a few ms apart); not changed.
  - Tested (scratch kino server on 5199 with fake sessions, Rind driving the runtime on an Xvfb display, CDP into both halves; 22 checks): each half signed in as its own account with separate local storage, seat info and tags, F8/F9, player 1 opening Kino hosted a room and player 2 followed into it, Kino loaded in both (39 s, GTX 1660 Ti), the host started and player 2 went in without a click, a fake controller moved player 2 only, blur paused player 1 only (more in Rind's CLAUDE.md).

## Helm rooms (2026-10-19)

- Helm (`~/projects/helm`, a program in Rind: the user's control room for Claude Code sessions) lets friends watch peer to peer, the way Melonopoly plays: the Helm server holds a co-op room with `page: '/helm/'` (`map: 'Helm'`), joined as the owner (their `kino_session`, handed over by Rind), and a viewer's Rind joins it only for the WebRTC handshake (or the relay fallback), then leaves, so the 4-player limit isn't a viewer limit.
- `GET /api/helm` (signed in) lists the Helm rooms whose host is the caller or one of their friends: `{rooms: [{code, owner: {id, name, picture}, me}]}`. Anyone can still join a Helm room by code (`/api/ws` join); Helm itself decides what each viewer may see from the joiner's `uid`.

## Game tokens and Night Shift (2026-10-21)

- Native games that Rind starts can't use the site cookie. Instead, Rind fetches **`GET /api/game-token?game=<id>`** (signed in; `id` matches `^[a-z0-9-]{1,40}$`) with the account's cookie and hands the token to the game (Rind's catalog template `{token}`, catalog api 2).
  - Token: `b64url(JSON {v:1, g: game, u: pubId, n: name, p: picture, e: expiry ms}) + '.' + b64url(HMAC-SHA256)`, valid 24 h.
  - The key is `DATA/game-token.key` (32 random bytes, mode 600, made on first use, kept across restarts; deleting it voids every token).
  - `readGameToken(token, game)` checks the signature (timing-safe), the game and the expiry.
- **Night Shift** (`~/projects/opsec`, a co-op sysadmin game on real OpenBSD boxes) has its own game server, which kino fronts on its unix socket `OPSEC_SOCKET` (default `/opsec/opsec.sock`; the quadlet mounts `~/.local/share/opsec/sock` there).
  - `/api/opsec/*` is proxied with the prefix stripped (`/api/opsec/leaderboard` → `/leaderboard`, query kept). The cookie and any `x-opsec-*` headers are dropped. If the socket is down, the answer is 503.
  - The WebSocket `/api/opsec/ws` needs the token in `X-Opsec-Token` (401 otherwise; native clients send no Origin, a foreign Origin is refused).
  - The upgrade is replayed to the socket as `/ws` with `X-Opsec-User: b64url(JSON {id, name, picture, owner, friendOfOwner, friends: [pids]})`, without the token or cookie, then piped both ways.
  - `OPSEC_OWNER` = the site owner's pid (Helm's `ownerPid`). The game server decides who may play (friends-only) from `owner`/`friendOfOwner`.
- Tested 2026-10-21 against a scratch server (port 5199, fake owner/friend/stranger sessions, a stub game server on a scratch socket), 17 checks:
  - token issue, 401 without a cookie, the key file;
  - identity for owner/friend/stranger, frames both ways, a spoofed `X-Opsec-User` dropped;
  - bad/expired/other-game tokens and a foreign Origin refused;
  - the HTTP proxy;
  - 503 with the socket gone;
  - the key reused after a restart.
