# Fork setup and hosting

- Branch `custom` holds local work. The `upstream` remote is the original repo; update with `git fetch upstream && git merge upstream/main && git lfs pull`. The `origin` remote is the user's backup fork https://github.com/darkmedic043/kino-der-toten (public, because forks of public repos must be; default branch `custom`). Push `custom` there after committing. LFS objects are shared with the upstream fork network, so pushes upload only new LFS files.
- **Public URL**: https://zombies.terminallysleepy.com, through the user's own locally managed Cloudflare tunnel `deskpet-memory` (`~/.cloudflared/config.yml`, user service `cloudflared-deskpet-memory.service`; the ingress was added before the 404 catch-all, and the pre-change backup is `config.yml.bak-kino`). The root `cloudflared.service` runs a different, dashboard-managed tunnel; leave it alone.
- **Accounts**: `.tools/kino-server.mjs` replaced `serve.mjs` in the quadlet. It serves static files plus `/api/{config,me,auth/discord,auth/discord/callback,auth/logout,profile}`. Discord OAuth2 uses the code flow with scope `identify`: a one-time `state` cookie (`kino_oauth`, path `/api/auth`, 10 min), the code is exchanged server-side, and `/users/@me` supplies the name and avatar; the session sub is `discord:<id>`. Sessions are an HttpOnly cookie (90 days, `Secure` behind https). Data lives in `~/.local/share/kino` (bound to `/data`: `sessions.json`, `profiles/<sha256(sub)>.json`). Cross-origin non-GET requests are refused. Credentials `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET` are in `~/.config/kino/discord.env` (mode 600, outside git, loaded via the quadlet `EnvironmentFile`); `KINO_PUBLIC_URL` is set in the quadlet, and the redirect is `<public>/api/auth/discord/callback`, registered in the Discord developer portal. Never print or commit the secret. Caching: the zone's Browser Cache TTL rewrites `no-cache` to `max-age=14400`, so the server sends `no-store` for html/js/css/json/md/txt/yml (yml: the Rind launcher's update feed in the git-ignored `export/web/rind/`; folders serve their `index.html`) (Cloudflare passes it through as BYPASS/DYNAMIC) and `public, max-age=86400` for heavy assets. Client side: `cloud.js` patches `localStorage.setItem` for `kino.mods.progression|settings|best*`, stamps `kino.cloud.updatedAt`, pushes after 2 s or on pagehide, and on load syncs newest-wins, except map rewards (`profile.rewards`), which only get added: `mergeRewards` in cloud.js takes the losing copy's, and the server's PUT keeps saved ones (`keepRewards`) so a stale open tab can't wipe them; `cloudReady` is awaited by home.js and the progression and characters mods. The local copy records its owner (`kino.cloud.owner`, the account's public id, 2026-10-19): when a different account signs in on the same browser, the tracked keys are dropped and that account's copy is pulled, so newest-wins never uploads one account's progress to another (the Rind launcher also keeps every account in its own storage). Sign-in only happens on the public origin; other origins show a link to it.
- **Cloud saves** (`export/web/cloud.js`, `.tools/save-guard.mjs`): the whole store of tracked keys is mirrored to `/api/profile`, one file per account. Newest stamp wins, so before 2026-11-01 any old device could replace the account's save: `migrate()` ran at module load and stamped the copy with the current time, so a browser last used on 10-22 looked newest and uploaded a ten-day-old save between 02:58 and 03:33 UTC on 11-01 (the Atlas 45 start became the old G18 start in the client log; the credits ledger and daily challenge stop at 10-22 09:33; career has no Nuketown entry although `kino.best.nuketown` survived, because a pull doesn't delete keys the server lacks). Rind then pulled it. Now: `migrate()` writes without stamping; each browser or Rind partition has a `kino.cloud.device` id and a `kino.cloud.base` (the server stamp it last saw); a device whose base is behind takes the server's copy whatever the clocks say; the server answers 409 to an upload not based on what it holds, unless that device wrote it (`staleUpload`). Refused uploads are filed, and the server keeps a copy of the save every 3 hours: `profiles/<id>.history/auto-*.json` (last 120, about 15 days) and `rejected-*.json` (last 10). To restore one: copy its `keys` into the profile file with `updatedAt` set to now and `device` removed, with every game page closed, since an open page writes its own copy back at `pagehide`. Two devices playing one account at once: the second one's progress lands in `rejected-*`, not in the save. Tests: `test/cloud-sync.test.mjs`.
- Served by the Podman quadlet `~/.config/containers/systemd/kino.container` (image `node:24-alpine`, checkout bind-mounted read-only at `/app`, running `.tools/kino-server.mjs 5190`) on **port 5190**. Port 5173, the upstream default, is used by the deskpet electron-vite dev server on this host. The server sends `Cache-Control: no-cache`, so file edits show up on a browser refresh without a restart.
- Git LFS is installed as a user binary at `~/.local/bin/git-lfs` (no system package). The LFS assets are about 1 GB.
- Host Node is 20 and upstream wants 24. `npm test` passes on 20 anyway. The container uses 24.
- No system browser is installed. Browser checks use Playwright's headless Chromium in `~/.cache/ms-playwright` with `--use-angle=swiftshader --enable-unsafe-swiftshader`. The upstream `.tools/test-*.mjs` scripts hard-code Windows Chrome paths, so they won't run as-is. Software WebGL is slow: hide the canvas before UI screenshots, and don't render Kino and another map in one browser at the same time.
- **DNS (2026-10-05)**: `kino.container` sets `DNS=10.64.0.1` (Mullvad's in-tunnel resolver; the host's VPN refuses other resolvers) and `DNS=192.168.1.1`. Without it, pasta's forwarder went stale after a host network change and Discord sign-in logged `discord sign-in: fetch failed` (EAI_AGAIN) for every attempt until a restart.
- **Rind launcher endpoints** (2026-10-07): `/api/install/melon-zombies` (redistributable files only, `.tools/install-manifest.mjs`), `/api/install/melon-pinball?platform=linux|win` (the published native build in git-ignored `export/web/rind/games/melon-pinball/<platform>/`), `/api/saves/<game>` (GET/PUT, signed in; `profiles/<hash>.saves-<game>.json`), `/api/leaderboard/melon-pinball` (the player and their friends: best score from scores.txt, best Harvest season from unlocks.txt, only those with either). Rind itself, its update feed and download page are under `export/web/rind/`. Details in ~/projects/rind/CLAUDE.md.

## Gzip copies (2026-11-02)
`.tools/kino-server.mjs` sends `<file>.gz` with `Content-Encoding: gzip` when the browser accepts gzip and the copy is newer than its file (maps are mostly raw vertex data and halve; Cloudflare doesn't cache `.glb`, so first loads go over the home uplink). Build them with `node .tools/build-gz.mjs` (every `.glb/.bin/.wasm/.json` over 256 KB under export/web; git-ignored). **Rerun it after rebuilding a map or weapon**, or that file is sent uncompressed (a stale copy is skipped, never served). Server changes need `systemctl --user restart kino`. A Cloudflare cache rule for `.glb`/`.ktx2` would take load off the uplink.
